# Input / controllers

## Product rules (§26)
Controller-first with logical actions, never controller-brand semantics. Required before the relevant final milestone: Controller Mapping, Input Tester, RGB Lighting where supported. Mapping reset belongs to Reset System Settings. Default face roles (2026-10-07): `menu_confirm` = BTN_SOUTH (bottom), `menu_back` = BTN_EAST (right), in controllersd defaults, inputd defaults/`input-bindings.conf`, tester and labels. Games are unaffected: the game gamepad emits `menu_confirm`→BTN_SOUTH and `menu_back`→BTN_EAST, so physical east stays RetroArch A. Extra logical actions: `face_north` (Favorite on Home, home-users-oob.md), `face_west` (Game Details, emulation.md §37.18). Game gamepads/hotkeys: emulation.md §37.13. Physical keyboard: ui.md §37.24.

## Controller mapping (§37.3)
- Controller mapping (owner `nuubos-controllersd`, D-Bus `org.nuubOS.Controllers1`): 17 button controls + `left_x/left_y/right_x/right_y`; each bound to one source `key:CODE`, `abs:CODE:+|-` (half axis; on a stick axis = normal/inverted), `abs:CODE:>|<` (full trigger travel from min/max) or `none`. Defaults are derived from the device's evdev capabilities (D-pad keys or hat, L2/R2 keys/Z-RZ/BRAKE-GAS, right stick RX/RY or Z/RZ); `/state/users/<u>/controllers/<hex-id>.conf` stores only differences (legacy `action=305` still read). Capture: `BeginRemap` → inputd sends `RAWBASE`/`RAWREADY` baselines (normalized -100..100) → stick vs trigger is told apart by rest position; 5 s timeout (`RemapCancelled`), any button cancels a stick capture; a source already in use is swapped (same kind) or unassigned (other kind). inputd only consumes the navigation actions + `left_x/left_y` (stick navigation) and parses the same format. Input Tester `InputEvent` carries the resolved logical control and value (buttons 0..100, sticks -100..100).
- Input Tester UI (settings-view 14, user request 2026-10-08): `ControllerTesterVisual` in home.slint draws a brand-free pad on a 360x200 grid scaled by `u` (top-aligned, M3 Theme tokens; triggers fill with analog travel, stick knobs move with the logical value). Below it the last-input chip and the exit combo `H + START` (i18n 740): controllersd ends the tester when Hotkey and Start are held together (`TesterExitRequested`), because the tested controller's Back is captured. Navigate/Select hints are hidden on that page. Headless: ui-shot scene `tester`.
## Select and face actions (2026-10-10)
- New logical action `select` (default BTN_SELECT 314 in inputd defaults and input-bindings.conf, controller mappings by the `select` control name), routed like the navigation actions: Home opens Find a Game.
- Home: North = Game Details (was West), on a collection Manage; West unused on Home. System keyboard: West = delete the last character.
- UI actions `tab_prev`/`tab_next` (2026-10-13): L2/R2 (`BTN_TL2`/`BTN_TR2`, 312/313; checked in the CubeXX gpio-keys capabilities) in `default_bindings` and `input-bindings.conf`, routed like the other navigation actions (Home while Settings/an app owns input, the Quick Menu while it is open). Used by the Media app's Music/Video sections.
- UI actions `page_prev`/`page_next` (2026-10-14): L1/R1 (`BTN_TL`/`BTN_TR`, 310/311), same routing; Home uses a double press for previous/next track while music plays (streaming-media.md). Not repeated when held.
- Analog stick poll rate (battery audit 2026-10-14): nuubos-inputd writes `/sys/class/input/eventN/device/poll` of `adc-joystick` devices: 4 ms (the device-tree rate) while a game owns the controllers, 32 ms in menus (stick navigation; 16 ms until 2026-10-20: measured on the CubeXX idle Home 2145 context switches/s at 16 ms vs 1154 at 100 ms, the poller kworkers 406 → 73/s; in a game 4 vs 8 ms changed nothing measurable in CPU, so games keep 4 ms), 100 ms while `/run/nuubos/screen-off` exists (inotify on /run/nuubos); written only when it differs, logged as `stick poll eventN M ms`. Kernel `0106` raises the poller maximum to 100 ms (before it equalled the device-tree value: EINVAL). H5 accepts 4/32/100 and checks `max` = 100.
- Rumble (user request 2026-10-18, "rumble must also work over Bluetooth"): the game gamepads (`nuubOS Gamepad`) declare `EV_FF`/`FF_RUMBLE` (`ff_effects_max` 16; uinput opened O_RDWR) and inputd serves the uinput FF protocol in its poll loop (`vpad_process`: `UI_FF_UPLOAD`/`UI_FF_ERASE` with BEGIN/END ioctls, `EV_FF` plays). An effect plays on every input of the same player that has `FF_RUMBLE` (inputs are opened O_RDWR): the controller's own evdev (kernel force feedback: xpad/hid-microsoft, hid-playstation, hid-nintendo...) and, for `builtin`, the `pwm-vibrator` device, only while rumbled's `INTERNAL_RUMBLE` (`/state/users/<id>/input-feedback.conf`, re-read on change) is on. Effects are uploaded to a target at its first play and again after an update (`ff_gen`); a rescan reopens the inputs and drops them, so they are uploaded again at the next play. Nothing rumbles under the Quick Menu (plays forced to 0, playing effects stopped by `vpad_release`); gamepads off erases them. Covers RetroArch, Moonlight and Steam Link (Valve's app rumbles the SDL gamepad). Log: `rumble target player=N path=...`, `rumble upload failed`. Not yet: controllers whose kernel driver has no force feedback (8BitDo Ultimate 2C over Bluetooth = hid-generic, `B: EV=b`): needs the controller's own output report (hidraw) or a kernel driver.
- Restart gotchas (2026-10-18): `S47nuubos-inputd stop` now waits for the daemon to exit (a `start` right after found the exiting process in the pidfile and started nothing: `deploy-target.sh -s` left the console without inputd); `restart` (handoff) was already fine. controllersd ignores SIGPIPE: an inputd restart used to kill it (pad maps written to the closed socket), and without it inputd creates no game gamepads (Steam Link: "no controllers"). After restarting inputd by hand, check `pidof nuubos-controllersd` and the `padmaps updated` line.

## Lost releases / "ghost input" (2026-10-21)
User + Reddit report (RG40XX V/V2, also in menus): "it starts moving by itself as if a button were held". Reproduced on the CubeXX with `tools/input-drop-test` (dev aid: a uinput pad presses D-pad Down, inputd reads it, then inputd is SIGSTOPped while ~1200 axis events and the release are written; `input-drop-test INPUTD_PID [settle_s] [ready_s] [unplug]`, wait ≥6 s after creating the pad: inputd reopens it once controllersd maps it and a reopen drops what was queued): the old inputd kept emitting `navigation-repeat action=menu_down` forever (Settings scrolled by itself), even after the pad was removed.
- Cause: inputd ignored `SYN_DROPPED`. When it falls behind, the kernel's per-client evdev buffer (small, ~64 events for the stick) overflows, the queued events are discarded and the release (or the stick's return to centre) is lost: the game gamepad keeps the button/axis held, the navigation repeat (inputd's own, stopped only by the matching release) keeps scrolling. The H700 adc-joystick is polled every 4 ms (DT `poll-interval`), so a moving stick fills that buffer in well under 100 ms of inputd delay.
- Fix: per input `keys` (last seen EV_KEY state, initialised with EVIOCGKEY at open) and `dropping`: from `SYN_DROPPED` to the next `SYN_REPORT` events are discarded, then `resync_input()` reads EVIOCGKEY/EVIOCGABS and replays the differences (keys) and every axis value through the same `process_events()` path (game gamepads, hotkeys, navigation). Log `input-dropped` / `input-resync replayed=N`. Safety net: `navigation_repeat_tick()` stops a repeat whose action is no longer held on any input (live EVIOCGKEY of the bound key, abs binding state, nav-axis direction) and broadcasts the missing release (`navigation-repeat stop ... reason=not-held`).
- Verified on the CubeXX with the tool: drop → resync replayed the release, no repeat. Removing a pad while a key is held already produced the release (the kernel releases keys on unregister). Not yet seen on the user's RG40XX V/V2 after the fix (needs play time); in-game path covered by the same replay, not separately measured.
- D-pad direction "stops responding, recovers after a while" (Reddit, RG SP, 1.0.0-rc.1, 2026-10-21; the reporter's setup not known: whether Bluetooth devices were connected). Mechanism that fits: the game gamepad's D-pad is a hat (`vpad_set_button`: x = right - left), so a direction left held on the game gamepad cancels the opposite one until it is pressed and released again. Ways a held state can go wrong besides `SYN_DROPPED` (unlikely on an SP: no sticks, gpio-keys evdev buffer 64 events): (1) any `/dev/input` create/delete (Bluetooth controller or headset/AVRCP connecting or sleeping, a uinput device) makes inputd `rescan_inputs()` close and reopen every input: events in the gap are lost and the new `keys` baseline comes from EVIOCGKEY, so a release in the gap is not replayed to the game gamepad; (2) the same change makes controllersd push PADMAP twice, and `commit_padmaps()` calls `release_all_vpads()`: a direction held at that moment is dropped until it is pressed again; (3) while the Quick Menu button is held every event is consumed, so a direction pressed during a chord and still held afterwards does not reach the game. Fix (2026-10-21): (1) `rescan_inputs()` keeps every input still there open with its state (`input_still_there`: same path, EVIOCGNAME answers with the same name, same `st_rdev`), opens only new nodes and closes only vanished ones (log `input-close`); (2) `commit_padmaps()` compares the new table with the current one (`changed=0|1` in the log; controllersd sends it 2-6 times per device change) and only on a real change releases the game gamepads and then replays what the players still hold through the new mapping (`replay_held_controls`: `keys` + EVIOCGABS through `forward_game_event`; not under the Quick Menu, the hotkey modifier or Web Mode). Case (3) left as is: replaying there would press a chord's button in the game. Reproduced and verified on the CubeXX with `tools/dpad-hold-test` (uinput pad holds Right in a running game, another device appears; `dpad-hold-test [ready_s] [pad]`, `pad` = the second device is a controller that gets a player): before, the nuubOS Gamepad's hat went 1 -> 0 while Right was still held; after, 1 stays 1 (remote and second controller), and a release made as a device appears still arrives (0).
- Input latency notes (audit 2026-10-21, not measured end to end): every gpio-keys button has the kernel default `debounce-interval` 5 ms (no DT sets it; sunxi pinctrl has no per-pin debounce, so gpio_keys uses its hrtimer: each press and release reaches evdev 5 ms after the last edge). RetroArch: `video_frame_delay` 0, run-ahead/preemptive frames off, no threaded video except NDS; the Dreamcast core's threaded rendering adds one frame by design (emulation.md).

## Bluetooth rumble: Xbox One S 1708 (2026-10-21)
User report: "Bluetooth rumble does not work" (Xbox Wireless Controller 045e:02fd, classic BT, firmware 9.03, BlueZ 5.86 with UHID). Diagnosis on the CubeXX with `tools/ff-test` (dev aid: `ff-test /dev/input/eventN|game|game2 [strong] [weak] [ms]`; `game`/`game2` turn inputd's game gamepads on like emud and play on player 1/2's nuubOS Gamepad): a raw report on `/dev/hidraw0` with enable 0x0f vibrated, the driver's report (enable 0x03, weak|strong only) is ignored by this firmware. Kernel patch 0018 (enable all four actuator bits for the 1708) had zero-context hunks written for the v0.5 kernel: on 7.3 its table hunk landed on the 8BitDo SN30 Pro+ entry, so the 1708 never got the quirk. Regenerated with context against 7.3 (the SN30 Pro+ back to upstream `MS_QUIRK_FF`); a scan of every kernel/package patch found no other zero-context hunk on an existing file (only libdisplay-info's one-line meson.build). Verified: player 1 (Xbox) through inputd rumbles and stops; player 2 (built-in) drives `pwm-vibrator`. Pitfalls: a direct EV_FF write to a controller is silently dropped while inputd grabs it (only the grabbing handle may inject); a hidraw report with loop count 0 rumbles forever (stop: `03 0f 00 00 00 00 00 00 00`).
