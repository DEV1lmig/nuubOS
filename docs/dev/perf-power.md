# Performance / power roadmap (H700 graphics and clocks)

Started 2026-10-28 (open-items RC4 item 14).

**CubeXX state (2026-10-28 evening):** normal: kernel #15 (shipped config, no debug hook), clean cmdline (no `slub_debug`/debug options), DCDC2 940 mV, GPU max 600 MHz, libgallium WITHOUT Mesa 0004 (an unstripped build: the next deploy/OTA replaces it; `/userdata/libgallium-0004.so` = the old one, do not reinstall); backups `/userdata/Image.pre-debug`, `/userdata/modules-7.3.0.pre-debug` can go. Goal: more performance and less battery drain by changing the stack where measurements justify it, tailored to the H700 (Mali-G31 MP1: one shader core, no AFBC; DE33 display engine planes and scalers; write-combined GPU buffers; shared LPDDR4), not just version updates (user, 2026-10-28). Stability comes first. **Keep the Status column current after every step** (this file is the hand-off between sessions); details of each finding go in the area file (emulation.md, platform.md, ui.md) and are linked here.

Status: `done`, `in progress`, `next`, `planned`, `rejected`.

## Facts the plan rests on (CubeXX, 2026-10-28)
- GPU OPPs 432/456/504/552/600 MHz, all at 940 mV on `vdd-gpu-sys` = AXP717 DCDC2 (reg 0x84, 0.5 V + n x 10 mV), a rail shared with the SoC "sys" domain; H616 datasheet: VDD_SYS 0.81-0.99 V recommended, 1.1 V absolute max (VDD_GPU too). Lower GPU clocks save little at a fixed voltage.
- CPU: 900 mV up to 1032 MHz, ~1.1 V at 1416 MHz; 480/720 MHz have the same 900 mV as 1032 (pointless, the Energy Model skips them).
- panfrost devfreq: simple_ondemand, upthreshold 45 % (jumps to 600 MHz early). Runtime PM suspends the GPU when idle (Home idle: GPU suspended).
- RetroArch is scanned out directly on the panel (XR24 720x720 plane, labwc 0 % GPU): no composition cost while playing without Quick Menu/OSD.
- Transaction elimination (CRC) is already on for render targets; no AFBC on this GPU; Mesa 25.1-26.0 bring no G31 performance work ([relnotes](https://docs.mesa3d.org/relnotes/26.0.0.html)): no Mesa upgrade for performance.
- Baseline survey (`tools/perf-power/glsurvey.sh`, user settings bezel + CRT on, mains): SNES 50 fps, CPU 40 % of a core, GPU fragment 39 %; GBA 60 / 41 % / 21 %; PS1 50 / 43 % / 39 %; N64 (Mario Kart PAL) 50 / 62 % / 39 %, GPU at 600 MHz 98 % of the time; NDS 60 / 109 %. 2D games spend ~39 % of the GPU only on presentation (bezel bands + CRT pass at 720x720).
- No battery run-down measurements (user decision 2026-10-28: we do not need to know how much; lower clocks/voltage at the same fps obviously draw less). Judge changes by clock/voltage residency, GPU/CPU busy and fps (glsurvey.sh). The AXP717 cannot read power on battery anyway (platform.md).

## Rejected (do not repeat without new evidence)
- Mesa upgrade for performance (no G31 work upstream, see Facts).
- Lowering `vdd-gpu-sys` or GPU DVFS with voltage (shared rail, corruption history).
- CPU OPPs below 1032 MHz (same voltage), schedutil `rate_limit_us` raise (platform.md idle audit), Mesa glthread, Mesa busy-texture shadowing, tiler masks other than Mesa 0003 (emulation.md).
- Keeping the CPU mapping of cached BOs in Mesa, in any form: 2026-10-14 variant, Mesa 0004 of 2026-10-21 (purgeable) and its 2026-10-28 rewrite (never purgeable) all multiplied the page corruption of step 1.1; 0004 dropped 2026-10-28. Not the root cause (the corruption exists without it, step 1.1 (c)), but it multiplies it.
