# Platform: kernel, image, storage, display, power

## Kernel / hardware (§9.1)
Linux mainline 7.2.x. 7.2.8 passed the Dockerized build and the RG40XX-V quick regression: 143 PASS / 0 WARN / 0 FAIL / 9 SKIP (foundation, DRM/Panfrost/display/backlight, analog audio baseline, Cedrus/VPU, RTL8821CS Wi-Fi 5 GHz, Bluetooth, input/rumble capabilities, storage/STATE/USERDATA/USB, RGB). Newer repo/test records are authoritative.

## Universal H700 image (§9.2)
One image, device chosen explicitly by `DEVICE=` in `NUUBOS_BOOT/nuubos.conf`. Selectors: rg-sp rg28xx rg34xx rg34xx-sp rg34xx-sp-v2 rg35xx-2024 rg35xx-2024-v6 rg35xx-h rg35xx-h-v6 rg35xx-plus rg35xx-plus-v6 rg35xx-pro rg35xx-sp rg35xx-sp-v2 rg40xx-h rg40xx-h-v2 rg40xx-v rg40xx-v-v2 rgcubexx. RG40XX-V V2 uses `rg40xx-v-v2` where the repo expects it; never silently substitute another board profile. Empty/invalid DEVICE must fail safely, never boot a random DTB.

## Family display/lid matrix (2026-10-11)
- Panels: 640x480 (RG35XX family, RG40XX-H/V, RG28XX), 720x480 (RG34XX, RG34XX-SP), 720x720 (RG CubeXX, 36 MHz = 60.0 Hz, a 120 Hz mode exists, the preferred 60 Hz one is used). Output scale (`nuubos-wl-output-apply panel_scale`): 1.125 for 720x720 and 720x480 (both ~255 ppi vs RG40XX-V ~200 ppi: 640x640 / 640x427 logical), else 1. ui-shot renders 720x480 too.
- RG28XX: its ST7701 panel is 480x640 mounted sideways. Device tree `rotation = <270>` (0020, as ROCKNIX) gives the connector "panel orientation" = Left Side Up; labwc never applied it: `package/nuubos/labwc/0004` sets `wlr_drm_connector_get_panel_orientation()` (transform 90) when a DRM output is enabled and draws its first-frame splash at the logical size; nuubos-splash reads the property and rotates the KMS and fbdev splash exactly as wlroots renders. Not hardware-qualified (no RG28XX on the bench); games are composited by labwc (no direct scan-out through a rotation).
- Clamshells (RG35XX-SP, RG34XX-SP, RG-SP and their v2 panels): gpio-keys `SW_LID` on PE7, wake source on lid open (upstream DT). nuubos-systemd owns the policy (system.md "Lid").

## Storage (§9.3)
SYSTEM (boot/root), STATE, USERDATA; SYSTEM/STATE never exposed as user storage. A non-nuubOS-owned TF2 is never formatted automatically; formatting needs explicit user confirmation; migration/backup transactional and verifiable.

## Display (§22)
Initial brightness 60%; user brightness persists across reboot. Display state stays coherent across HDMI/internal panel changes: unrelated setting changes must not resurrect stale internal-panel brightness presentation while the panel is inactive.

## RGB (§27), battery/status (§28)
RGB depends on hardware capability: no controls for unsupported devices (rows show "Unavailable"); integrate with lifecycle/power. Battery/status is event-driven: AXP717 uses gauge events (`GAUGE_NEW_SOC`), not UI polling; keep that unless the driver/API requires otherwise.

## RGB Lighting redesign (user request 2026-10-08)
- `nuubos-rgbd` is only the hardware frame sink: persistent line protocol on `/run/nuubos/rgbd.sock` (`STATUS`, `FRAME` in LOGICAL order = zone by zone, position by position around the ring, mapped to physical LEDs through `led_indexes` in `rgb_common.c`, `OFF` = MCU + LED rail unpowered). No animation, brightness or policy there. `nuubos-rgbctl status|off|color R G B|locate N|frame ...` is a dev tool; `locate N` lights ring position N white and N+1 dim to qualify ring start/direction.
- `nuubos-lightingd` renders every frame (time-based, gamma 2.2, brightness 10..100 in steps of 10 as a perceptual gain; 30 fps timer only while something moves, nothing between events; MCU powered off when the ring is dark). Contract and event table in the header of `lightingd.c`; Home side in `nuubui-home/src/src/lighting.rs`.
- Effects (per user, `lighting.conf` FORMAT=2): Off, Solid, Breathing, Orbit, Aurora (default since 2026-10-11, user request: Aurora in the user's Mood accent, `COLOR=theme`; before Off; only users without a saved `lighting.conf` get it), Spectrum, Battery Level (gauge, charging LED pulses), Console Colors (colour of the running game's system from `systems.conf` field 6, via emud `SUBSCRIBE`; theme accent outside games). Colour = theme accent (read from the active user's theme, follows theme changes) or a fixed palette (same list in `lighting.rs` COLORS and `lighting-color-index()` in home.slint). Effect/colour dropdowns preview live on the LEDs (`Preview`/`EndPreview`, never persisted). Old v1 files (MODE/RED/GREEN/BLUE/SYSTEM_EFFECTS) are migrated on load. Without RGB hardware (`supported`=false) Settings → Controllers & Input has no RGB Lighting row and the section header is RUMBLE (string 899), also on the web page.
- Tasks layer (user request 2026-10-09): while a Live Notification runs (`progress=` in a POST/UPDATE; ended by a message for the same id without progress or DISMISS) and the user's tasks category is on, the ring shows the oldest one over the effect, under signals: accent gauge to the progress with a breathing head LED, or a slow accent comet when the progress is -1; crossfades in/out; frame timer runs while it is shown. The list is rebuilt from notifyd's replay at every (re)SUBSCRIBE. The completion still plays the tasks signal (fill/pulses).
- System signals: five per-user categories (power, battery, connections, games, tasks), sourced from the EPIC-006 notification stream (`SUBSCRIBE` to notifyd: only POST starts a signal, Live Notifications only on completion) plus `Lifecycle(sleep|wake|shutdown)` from `lifecycle-lighting`. Grammar: one shape per meaning (link/unlink for connections, pulses for warning/error, fill for success/charging, spin for save/load state, flash for screenshots, tick for save slot, welcome/wake/farewell for power) and colour roles accent/success/warning/error/neutral. Enabling a category plays its signal. Priority: power > errors > warnings > info.
- Lifecycle is runtime-only (the 0.5 hook persisted brightness 0 during sleep): `sleep` fades and replies once dark, `wake` is ignored unless dark/darkening (systemd sends it at start-up and after a failed power off). `boot`, `restart`/`reboot`, `poweroff` (= legacy `shutdown`) are the LED side of the lifecycle splash animations, timed like them (ui.md "Lifecycle splash").
- Ring order (every topology in `rgb_common.c`): position 0 = upper right LED, clockwise, 45 degrees apart, position 3 at the bottom (lightingd `RING_BOTTOM`). CubeXX qualified 2026-10-11: left ring `{15..8}`, right `{1, 0, 7..2}` (the two rings are wired in opposite directions). Diffused rings make neighbouring LEDs hard to tell apart: qualify with two LEDs 90 degrees apart in different colours (`nuubos-rgbctl frame` with position 0 white and position 2 red: expected at about 1:30 and 4:30), reported as clock positions, not with `locate`.
- To qualify on hardware: RG40XX-V ring with the same two-LED frame, colour balance of the palette, effects/signal timings on the real LEDs, sleep/wake/restart/power off sequences.

## Performance / power principles (§31)
H700 is constrained: optimize intentionally, not prematurely; keep proven hardware decisions unless new measurements justify change. Profiles Auto / Performance / Battery Saver are policy of the system service, never UI pages. Suspend/power changes need regression testing (Wi-Fi, Bluetooth, input wake, display, storage, audio interact). Never invent wake behavior beyond qualified hardware capability.

## Kernel, display and suspend notes (§37.4)
- Kernel-stage limitation: with HDMI connected at boot the DRM fbdev is created at the mode common to panel and HDMI (640x480), so the kernel boot/poweroff splash appears small on HDMI. Fixing it needs a KMS-based splash path (platform work).
- Boot-with-HDMI → unplug → black panel (`sun50i-iommu ... Page fault (master 0, dir rd)` on each CRTC switch): root cause is `commit_tail_rpm` (ACTIVE_ONLY) skipping planes disabled together with their CRTC, so sun8i layers kept a freed/unmapped IOVA enabled and the DE faulted on the next CRTC enable. Fix: kernel patch `0026-drm-sun4i-disable-layers-with-their-crtc.patch` (2026-10-05).
- Boot-with-HDMI → panel black for the whole boot (backlight on, every SoC register identical to a good boot; even the TCON colour-bar test pattern stayed black): TCON LCD0 and TCON TV0 share `pll-video0`; all CRTCs are mode set before any is enabled and the TCON took rate exclusivity only at enable, so the HDMI mode set retuned the PLL and the panel was initialised at 99 MHz instead of 27 MHz. Fix: `0027-drm-sun4i-tcon-lock-dclk-rate-at-mode-set.patch` (rate exclusive from mode set; HDMI then moves to `pll-video1`). Hardware-confirmed 2026-10-05. Boot-without-HDMI → plug → unplug always worked because the panel already held the PLL.
- Sleep → spontaneous wake after ~1 min (seen as "Wi-Fi lost" toast + screen back on): the AXP717 IRQ line is wake-armed (power key shares it), so the `GAUGE_NEW_SOC` IRQ added by patch 0100 ended s2idle on every 1% SOC step. Fix: `0101-power-supply-axp717-mask-soc-irq-during-suspend.patch` (SOC IRQ disabled in suspend, one `power_supply_changed` on resume). To find a wake source: diff `/proc/interrupts` across the sleep and read `/sys/class/wakeup/*/last_change_ms`. Wi-Fi deauth during suspend (`DEAUTH_LEAVING`) is normal: rtw88 has no WoWLAN.
- Short black flash on every composition→direct-scan-out switch: DE33 mixer commit writes no `SUN8I_MIXER_GLOBAL_DBUFF`, so layer attributes and address do not latch together; fixed for the bottom layer by `0028-drm-sun4i-ignore-pixel-alpha-on-bottom-layer.patch` (2026-10-06, see §37.12). Any other per-frame attribute change on upper layers can still tear for one frame.
- Display clock check: `/sys/kernel/debug/clk/clk_summary` (pll-video0/tcon-lcd0/tcon-data-clock must read 81/81/27 MHz on the RG40XX-V panel).
- Display register debugging: `/sys/kernel/debug/regmap/{6511000,6515000}.lcd-controller/registers` and `*.mixer-top` are safe to read. NEVER read `1100000.planes-planes` or `*.mixer-mixer` regmaps: the read segfaults or hangs the whole SoC (target unreachable, needs a power cycle). Leave `drm.debug` at 0 on target; a high level during a modeset also locked it up. Single registers can be read with `devmem` (DE33: mixer0 blender 0x1281000, mixer top 0x1008100/0x1008140, channel N at 0x1101000 + N*0x20000, channel map 0x1008024..; TCON0_CTL 0x6511040 — writing source-select 1 shows colour bars). The kernel has no ftrace/kprobes: for call tracing add temporary `dev_info` and remove it after.
- Sleep aborted with a GPU client rendering (game): panfrost refused system suspend with -EBUSY when a job was still queued at freeze; `0029-drm-panfrost-wait-for-jobs-before-system-suspend.patch` (2026-10-08) polls `panfrost_jm_is_idle()` up to 1 s before `pm_runtime_force_suspend` (warns "jobs still running at suspend" on timeout). panfrost is a module: deploy `panfrost.ko`, reboot.
- HDMI with the TV in standby at connection/boot (LG 4K, 2026-10-08): HPD is high but DDC does not answer, the EDID read fails (`/sys/class/drm/card0-HDMI-A-1/edid` = 0 bytes, wlr-randr name `(null)`) and DRM offers only the no-EDID fallback modes (1024x768 current). Nothing retries when the TV wakes: `echo detect > .../status` re-reads the EDID but sends no `HOTPLUG=1` uevent, so wlroots (rescans connectors only on that) keeps the stale modes; restarting labwc picks them up. Fix: `0030-drm-bridge-dw-hdmi-retry-edid-while-hpd-high.patch` (2026-10-08): a failed EDID read with HPD high starts a delayed work that probes DDC every 2 s (`drm_probe_ddc`, stops when HPD drops) and sends `drm_kms_helper_hotplug_event` once the sink answers (dmesg `sink answers on DDC now, re-probing`); at most 3 such events per plug if the EDID still fails. dw-hdmi is built in: deploy `Image`. Needs hardware qualification with the TV in standby at boot.
- DE33 plane scaling (2026-10-08): `sun50i_h616_planes_quirks` shipped `scaler_mask = 0` ("driver needs improvements"); the VI channels already had the DE33 VI scaler path (`DE33_VI_SCALER_UNIT_BASE` 0x4000 + ch * 0x20000, control register written on every VI update), so `0031-drm-sun4i-de33-enable-vi-channel-scaling.patch` enables scaling on VI channels 0-2 only (UI channels have the VSU8 scaler the driver does not program correctly yet). The HDMI primary plane is VI channel 2 (mixer 1 map {1, 2, 8}); the panel's is UI channel 6 (unscaled). Verified: 640x360 buffer scanned out to 1920x1080, no IOMMU/GPU errors.
- DE33 VI scalers (2026-10-09, from the Allwinner BSP de330 driver, orangepi-xunlong/linux-orangepi branch orange-pi-4.9-sun50iw9, `disp2/disp/de/lowlevel_v33x/de330/de_vsu.c` + `de330_feat.c`): channel 0 VSU_ED (8/4 taps), channel 1 VSU10 (8/4), channel 2 VSU8 (4 horizontal, 2 vertical taps; banks only YHCOEFF0 0x200, YVCOEFF 0x400, CHCOEFF0 0x600, all lan2; scale mode 0 for RGB). Mainline programmed VSU8 like DE3 (8-tap lan3 left half as the horizontal filter, taps not summing to 1.0): scaled HDMI planes (UI and games) had a dark grille ('CRT effect' seen in nuubUI), looked darker overall and shimmered. Kernel `0033-drm-sun4i-de33-program-vsu8-scaler-as-4-2-tap.patch` fixes it (user-confirmed 2026-10-09: no CRT look). DE33 latches only the buffer address at frame start; scaler sizes/steps/phases/coefficients act at once, and the driver rewrote them (plus COEFF_RDY) on every flip: occasional tear while scrolling. `0034-drm-sun4i-de33-keep-vi-scaler-when-unchanged.patch` keeps the scaler when its parameters are unchanged (hardware confirmation pending). `0035-drm-sun4i-de33-latch-address-on-any-geometry-change.patch` extends 0032 (address first, one vblank, then size/pitch) to any change of source/on-screen size, pitch or format: going back from composition to the scaled client scan-out (a notification going away) flashed black (user report 2026-10-09; hardware confirmation pending).
- DE33 latching: layer size, pitch and format act at once, the buffer address only at the next frame (also why `0028` exists). Growing a layer (leaving a scaled game: 640x360 buffer -> 1920x1080 desktop) read the new size/pitch from the old buffer for the rest of the frame: one IOMMU read fault (`master 0, dir rd`, fault = old buffer + just past its end) on every scaled-game exit. `0032-drm-sun4i-de33-latch-address-before-growing-layer.patch`: when a VI/UI layer grows on an active CRTC without modeset, write only the new address, `drm_crtc_wait_one_vblank`, then the rest (0 faults in 4 exits; at most one frame of delay on those rare commits). Diagnosed with `echo 0x2 > /sys/module/drm/parameters/debug` (driver messages only, no modeset) around the exit.
- 2160p60 HDMI output: right after the UI came up at 3840x2160 (scale 3), panfrost logged `gpu sched timeout` on fragment jobs and a WARN in `panfrost_mmu_map` while a game started (RetroArch then hung and was killed). Not investigated; the output policy no longer uses modes above 1080 lines.
## Battery health (2026-10-10)
AXP717 exposes `health` (Good/Overheat/Cold/Dead/...) but no design capacity or cycle count: statusd publishes `BATTERY_HEALTH` (lowercase, dashes) and Settings → Power shows it localized; nothing more is measurable on this PMIC.

## USB-C charging and AXP717 registers (2026-10-11)
- Some USB-C chargers do not charge with a C-to-C cable (USB `online`=0, no VBUS) while USB-A→C cables and PC ports always work. Hardware: the board presents no Type-C sink Rd, so spec-compliant sources keep VBUS off; "permissive" chargers give 5 V anyway. The AXP717 Type-C block is disabled by eFuse (`0x0B` bit 3 = 0, `0xE3` = 0x00); enabling it live (`0x0B`=0x1D, `0xE3`=0x11 SINK) left `0xE7` in DISABLE and a failing charger still did not charge (A/B tested on RG40XX-V): no software fix. No USB PD either (no PD controller, 5 V charger only). Workaround for users: USB-A→C cable or a C→A adapter.
- Power-on source: `0x20` = 0x04 after a VBUS-insert boot, 0x01 after a power-key boot (datasheet REG 20).
- Charging on/off: writing `Not charging`/`Charging` to `axp20x-battery/status` clears/sets `0x19` bit 1 (mainline driver; the current reads ~0 net, raw ~400 mA offset). CV limit `0x64`: 0=4.0 V, 1=4.1 V, 2=4.2 V. AXP717 never reports `Full`: the PMIC standby state maps to `Not charging`.
- PMIC registers: `/sys/kernel/debug/regmap/0-0034/registers` (cached) or `i2cget -f -y 0 0x34 <reg>` (live).

## Charge limit and charge screen (user request 2026-10-11)
- Charge limit: kernel `0102-power-supply-axp717-charge-limit.patch` adds the standard `charge_control_end_threshold` (50..100, default 100 at every probe, which also re-enables charging) to the AXP717 battery. The driver applies it on every `GAUGE_NEW_SOC` IRQ and on every write: charging stops at the limit (`0x19` bit 1) and resumes 5 points below it. `status` reads `Full` while the limit holds charging, or in PMIC standby on VBUS at 100 % (before this patch the AXP717 never reported Full). In s2idle the SOC IRQ is masked (0101), and at power off nothing watches the gauge, so the driver then lowers the CV to 4.1 V when the limit is ≤90 % and charging is not held (approximately 90 %; restored on resume, and by the DT `voltage-max-design` at probe). A limit already held stays held at power off. To verify on hardware: what the gauge reads after a charge that ended at the 4.1 V cap.
- Setting: nuubos-systemd `CHARGE_LIMIT` (80..100 in steps of 5, default 100), `SET CHARGE_LIMIT n`, STATUS `charge_limit=` + `charge_limit.supported=` (whether the attribute exists). Applied when systemd starts and on SET. UI: Settings → Power row 5 and the web Power page (`system.chargelimit`).
- Charge screen: `nuubos-charge` (nuubos-splash package) runs from `S08nuubos-charge`, which blocks rcS. It shows the screen only when REG 20 has VBUS (0x04) and not the key (0x01); a software reboot reads 0. A battery must be present and the charger online, otherwise boot continues. The screen shows the splash wordmark, with the track as the gauge (dimmed above the limit, limit label under its edge), the percentage and the voltage, and digits only, so nothing needs localizing. The gauge goes red→orange→green relative to the limit, the same on the RGB rings through rgbd FRAME (lightingd is not running yet). The program writes CHARGE_LIMIT to the kernel itself because systemd is not up.
- Charge screen behaviour: the screen goes dark after 20 s (backlight `bl_power` plus CRTC off), and any key turns it back on. Power (any time) or Start (screen on) redraws the boot raster, keeps the DRM device held until ui-ready, and lets boot continue. Unplugging runs `poweroff`. The LEDs are dark with the screen, except a full ring when charging is complete. Events: power_supply uevents, plus a 5 s voltage refresh only while the screen is on. Host preview: `nuubos-charge --ppm FILE W H PERCENT MV LIMIT FULL`. Live test: stop the UI, then `nuubos-charge --force`.
